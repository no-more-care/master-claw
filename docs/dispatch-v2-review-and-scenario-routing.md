# Ревизия диспетчеризации после итерации 1 и переход на сценарный роутинг

> Статус: сценарная миграция завершена 2026-07-14, ветка `develop-v2`. Закрыты хотфиксы
> 2.1, 2.2, 2.5 и 2.6; все сценарии используют `ScenarioId`/`CommandId`, дерево
> `resolve_scenario`, per-scenario explicit-лексиконы и динамический закрытый контракт
> `StateDecision`. Удалены legacy `MessageIntent`, общий post-gate, глобальные матчеры,
> структурные pre-checks и Левенштейн. `MessageApplication` сокращён до тонкого facade;
> dispatch execution и обработчики разнесены по `app/handlers/`.
> Продолжение `docs/dispatch-refactoring-plan.md` (итерация 1 которого выполнена:
> `app/dispatch.py`, единый gate, фразы-как-данные, вариант B для review-стадии).
> Раздел 2 — дефекты, найденные при ревизии итерации 1. Раздел 3 — целевая
> архитектура «сценарного роутинга», снимающая класс этих дефектов целиком.

## 1. Оценка итерации 1

Выполнено честно: `decide()` — чистая функция с задокументированным порядком
приоритетов; `gate_intent` общий для фразовой и LLM-веток (есть тест); фразы вынесены
в таблицу данных с mode-фильтром; нечёткий матчинг ограничен и неоднозначность уходит
в LLM; review-стадия больше не трактует неизвестный ввод как ревизию; телеметрия
`source=...` + `gate=...`; 171 тест зелёные, ruff чистый.

Однако сохранена исходная парадигма «предварительных проверок»: глобальная цепочка
матчеров стоит ПЕРЕД деревом состояний и фильтруется гейтом ПОСЛЕ. Найденные ниже
дефекты — в основном следствия этой парадигмы, а не небрежности исполнения.

## 2. Найденные дефекты

### 2.1. [ВЫСОКИЙ] «Создай новый мир» при открытом review-черновике портит стейт воркспейса

Новая регрессия итерации 1 (в старом коде review-стадия глотала всё как REVISE и
ветка была недостижима).

Воспроизведение: воркспейс в стадии `review` → игрок пишет «создай новый мир» →
`match_world_workspace_action` не матчит → фразовый матчер → `WORLD_CREATION_REQUEST`
разрешён в `world_management` → `RunHandler(WORLD_CREATE)` →
`_handle_natural_world_creation` вызывает `save_world_workspace` **без проверки
существующего воркспейса**.

Последствия на уровне хранилища:

- `save_world_workspace` (sqlite.py, upsert по `world_id`) НЕ освобождает старый
  проект → в `world_projects` появляются **две строки с одним `active_channel_id`**;
- `world_workspace()` делает `fetchone()` **без ORDER BY** → какой проект получит
  следующее сообщение канала — не определено (на практике SQLite вернёт старый);
- старый черновик становится невозобновляемым: `resume_world_workspace` падает с
  «channel already has an active world project», а путь выбора draft-мира из каталога
  возвращает «world_not_ready» (проверка `project["channel_id"] is not None`).

Фикс (обязателен независимо от раздела 3, это защита данных):

1. UNIQUE partial index на `world_projects(active_channel_id) WHERE active_channel_id
   IS NOT NULL` — гонки и двойная активация становятся невозможными на уровне схемы;
2. в `_handle_natural_world_creation`: при открытом воркспейсе — `pause_world_workspace`
   текущего проекта перед созданием нового ЛИБО `Reject` с уточнением
   («сначала завершите/приостановите текущий черновик»); предпочтителен явный вопрос;
3. `world_workspace()` — добавить детерминированный ORDER BY + assert на единственность.

### 2.2. [СРЕДНИЙ] Collecting-стадия воркспейса глотает всё

Вариант B (уточнение вместо молчаливой ревизии) применён только к `review`.
В `collecting` default остался `REVISE`: «как работает бросок кубов» и «что ты умеешь»
уходят в LLM-пайплайн ревизии мира (проверено вызовом `decide()` напрямую).
План итерации 1 (шаг 6) требовал, чтобы вопрос по правилам отвечался в любом режиме
после воркспейса — в `collecting` он недостижим.

Фикс в текущей архитектуре: перед default `REVISE` в `collecting` пропускать
`is_explicit_rules_question` и help-фразы. В архитектуре раздела 3 проблема исчезает:
сценарий «редактирование мира» сам объявляет rules/help разрешёнными командами.

### 2.3. [СРЕДНИЙ] Per-mode маппинг фраз структурно невозможен — пункт 3.2 §4 плана выпал

`PHRASES` — глобальный словарь «фраза → интент». План требовал «одна фраза → разные
интенты по режиму» («что ты умеешь» → каталог миров в world_management, справка в
play). Фразу перенесли из WORLD_LIST в HELP: в PLAY стало правильно, но в
world_management она теперь идёт в LLM, и если тот вернёт `HELP_REQUEST` — gate
ответит «unavailable_world_management». Регрессия против старого поведения
(был детерминированный каталог миров).

### 2.4. [СРЕДНИЙ] Справка недоступна вне PLAY

`HELP_REQUEST` разрешён гейтом только в PLAY. «Помощь» в preparation или
world_management → LLM → отказ. Справка, как и `RULES_QUESTION`, должна быть
безусловно разрешённой во всех режимах, с рендером по режиму («в этом режиме вы
можете: ...»).

### 2.5. [НИЗКИЙ] Мёртвые команды `/game prepare` и `/world generate`

Реализованы в `_handle_command`, но `command_allowed` не пропускает их ни в одном
режиме — недостижимы через Discord (игра создаётся только выбором мира из каталога).
Существовало и до итерации 1, но теперь allowlist и обработчик — две явно
противоречащие таблицы. Решение: удалить ветки из `_handle_command` (или, если
команды нужны операторам, — внести в allowlist и покрыть тестом; сейчас они не
покрыты ничем).

### 2.6. [НИЗКИЙ] Голый `/advance` → «недоступно в режиме игры»

Старый код пропускал любой сабкоманд, и `_handle_command` возвращал usage-подсказку.
Новый allowlist `{raise, learn}` отклоняет `/advance` и `/advance status` с ложным
сообщением «команда недоступна». Фикс: неполная форма известной команды →
usage-подсказка, а не отказ по режиму (различать «команда неизвестна/запрещена в
режиме» и «команда известна, аргументы неполны»).

### 2.7. [КОСМЕТИКА]

- Две параллельные таблицы «режим → интенты»: `_ALLOWED_INTENTS` (dispatch.py) и
  `_INTENTS_BY_MODE` (deterministic_intents.py). Сегодня согласованы, завтра
  разъедутся. Нужен один источник (в разделе 3 им становится дескриптор сценария).
- `match_information_intent` живёт только ради старых тестов — пометить deprecated.
- Табличный тест приоритетов в `test_dispatch.py` — 7 строк; характеризационная
  таблица из шага 0 плана итерации 1 так и не появилась.

## 3. Архитектурное предложение: сценарный роутинг

### 3.1. Диагноз парадигмы

Текущая схема (и до, и после итерации 1):

```
глобальные матчеры фраз → decide() → gate (фильтр ПОСЛЕ) → обработчик
```

Дефекты 2.2–2.4 — один и тот же структурный изъян: **распознавание глобально,
ограничения накладываются постфактум**. Отсюда отказы «unavailable_...» на осмысленные
запросы, невозможность per-mode словарей и особые дыры на стыках (воркспейс).

Целевая схема — инверсия: **сначала дерево состояний выбирает сценарий, затем сценарий
сам определяет, что в нём можно распознать без LLM, а всё остальное уходит
стейт-модели с уже суженным пространством решений**:

```
state → Scenario (дерево состояний, детерминированно)
Scenario.explicit_commands  → точное совпадение → команда        (без LLM)
иначе                       → state-LLM(контекст, allowed_commands сценария)
                              → typed Command                     (LLM решает, НЕ отвечает)
Command → InfoCommand  → рендер из стейта (без LLM)
        → GmCommand    → reasoning/narrative пайплайны («гейммастер»)
        → Clarify      → уточняющий вопрос
```

Ключевые принципы:

1. **Никаких предварительных проверок до определения сценария.** Ни один текстовый
   матчер не выполняется, пока не известен сценарий. «Список миров» распознаваем
   только в сценарии выбора мира — в редакторе черновика этой команды в словаре
   просто нет.
2. **Явный базовый лексикон вместо нечёткого.** Детерминированно — только slash-команды
   и короткий список однозначных фраз точного совпадения (после нормализации),
   объявленный в дескрипторе сценария. Никакого Левенштейна: опечатки и
   перефразировки — работа стейт-модели, она для этого и существует.
3. **Стейт-модель решает, а не отвечает.** Она получает состояние + контекст и
   возвращает ровно одну команду из закрытого списка сценария. Она никогда не
   генерирует текст для игрока и никогда не прогоняет через себя данные листа/каталога:
   «игрок витиевато просит лист персонажа» → `SHOW_CHARACTER_SHEET`, рендер делает код.
4. **Отказ гейта исчезает как класс.** Модель физически не может выбрать команду вне
   сценария — enum в её output-схеме генерируется из `allowed_commands` сценария,
   валидация со retry уже есть в `BoundedJsonPipeline`. Пост-фильтр остаётся только
   как assert (нарушение = баг, лог, `Clarify`).

### 3.2. Дескриптор сценария

Сценарий — первоклассная сущность, единственный источник правды о том, что доступно:

```python
@dataclass(frozen=True, slots=True)
class Scenario:
    id: ScenarioId
    # точный лексикон: slash-команды и однозначные фразы → команда
    explicit_commands: Mapping[str, CommandId]        # нормализованная фраза → команда
    slash_commands: Mapping[tuple[str, str], CommandId]
    # закрытое пространство решений для стейт-модели
    llm_commands: frozenset[CommandId]
    # что подать стейт-модели (расширяет манифест INTENT_CLASSIFICATION)
    context_projections: tuple[str, ...]              # напр. ("current_scene", "actor_character")
    recent_chat_messages: int
    # куда падать при пустом/невалидном решении
    fallback: CommandId                               # обычно CLARIFY
```

Дерево состояний (расширение `ModeRouter`, по-прежнему без LLM):

```
game_id is None, воркспейса нет        → WORLD_SELECTION
game_id is None, воркспейс collecting  → WORLD_EDITING_COLLECTING
game_id is None, воркспейс review      → WORLD_EDITING_REVIEW
lifecycle draft/preparing              → PREPARATION
lifecycle active, pending нет          → PLAY
lifecycle active, pending есть         → PLAY_PENDING(kind)   # свой узкий сценарий
resumed roll confirmation              → ROLL_RESUME          # вне очереди, по event_id
```

Примеры наполнения (иллюстрация, не полный список):

| Сценарий | explicit (точно) | llm_commands | Примечание |
|---|---|---|---|
| WORLD_SELECTION | «покажи миры», «список миров», `/world create` | SHOW_WORLD_CATALOG, SELECT_WORLD(arg), CREATE_WORLD, SHOW_RULES, SHOW_HELP, CLARIFY | выбор мира по названию — тоже решение модели (`SELECT_WORLD` c аргументом), нечёткий матчинг заголовков уходит из кода |
| WORLD_EDITING_REVIEW | «подтверждаю мир», «сгенерируй», «выйти» | REVISE_WORLD, REGENERATE, CONFIRM_WORLD, EXIT_EDITOR, SHOW_WORLD_SETTINGS, SHOW_RULES, SHOW_HELP, CLARIFY | SHOW_WORLD_CATALOG отсутствует → «покажи миры» в редакторе = решает модель между CLARIFY/EXIT_EDITOR, а не тихий рендер каталога |
| PLAY | `/game status`, `/xp status`, «покажи персонажа» | DECLARE_ACTION, PLAYER_NARRATION, SHOW_CHARACTER_SHEET, SHOW_SCENE, SHOW_XP, SHOW_GAME_STATUS, ASK_SCENE_QUESTION, ASK_RULES, REQUEST_ADVANCEMENT, SHOW_HELP, CLARIFY | |
| PLAY_PENDING(pool) | «да», «нет», числа | ANSWER_PENDING, CANCEL_PENDING, SHOW_CHARACTER_SHEET, ASK_RULES, CLARIFY | модель видит текст pending-запроса и решает, ответ это или сторонняя просьба |

`SHOW_RULES`, `SHOW_HELP`, `CLARIFY` входят в **каждый** сценарий по построению —
дефекты 2.2–2.4 исчезают структурно, а не точечными фиксами.

### 3.3. Контракт стейт-модели

Роль: `ModelRole.STATE` (дёшево, быстро). Один пайплайн, но output-схема формируется
per-сценарий:

Вход (через существующий `ContextAssembler`, манифест собирается из дескриптора):

- сценарий и его причина (`mode_reason`);
- проекция состояния мира/игры (то, что уже есть: `mode`, `world_workspace`,
  `pending_interaction` + `context_projections` сценария — сцена, персонаж);
- последние N сообщений чата (сейчас 2 — для «витиеватых» запросов поднять до 4–6);
- текст висящего pending-запроса, если есть.

Выход (Pydantic, `extra="forbid"`):

```python
class StateDecision(BaseModel):
    command: CommandId          # Literal[...] из llm_commands сценария
    argument: str | None        # напр. название мира для SELECT_WORLD
    confidence: float
    evidence: str
```

Системный промпт фиксирует роль: «ты определяешь, какую команду выполнить; ты не
отвечаешь игроку, не выдаёшь информацию, не резолвишь действия». Это уже почти
дословно текущий промпт intent-пайплайна — меняется только то, что список допустимых
команд подаётся per-запрос, а не зашит глобально.

### 3.4. Два класса команд

```python
InfoCommand: SHOW_* — рендер из стейта, без LLM, дешёвый и мгновенный.
GmCommand:   DECLARE_ACTION, ASK_SCENE_QUESTION, REVISE_WORLD, ... —
             передача «гейммастеру»: reasoning/narrative пайплайны с их манифестами.
```

Диспетчер после решения тривиален: `COMMAND_TABLE[command](message, state)` — плоская
таблица вместо 20 `if` в `_dispatch`. Появление новой команды = строка в дескрипторе
сценария + строка в таблице + тест.

### 3.5. Что это даёт по сравнению с итерацией 1

| Проблема | Итерация 1 | Сценарный роутинг |
|---|---|---|
| фраза значит разное в разных режимах (2.3) | невозможно (глобальный словарь) | тривиально: лексиконы per-сценарий |
| отказ «unavailable» на осмысленный запрос (2.4) | gate-фильтр после распознавания | модель выбирает только из допустимого |
| стыки воркспейса (2.1, 2.2) | точечные дефолты и fallthrough | у редактора свой закрытый сценарий |
| Левенштейн и его коллизии | смягчено порогами | удалён; перефразировки — работа модели |
| две таблицы «режим→интенты» (2.7) | ручная синхронизация | один дескриптор на сценарий |
| стоимость | LLM-вызов на всё нераспознанное | та же модель STATE-роли; детерминированный лексикон продолжает отсекать частые фразы без вызова |

Цена: +1 дешёвый LLM-вызов там, где раньше «спасал» нечёткий матчинг. Это осознанный
размен: молчаливо-неверная детерминированная трактовка дороже (см. 2.1).

## 4. План работ

Статус выполнения: пункты 1–5 завершены, включая демонтаж legacy-роутинга и перенос
обработчиков в `app/handlers/`. Автоматическая приёмка из пункта 6 проходит; живой
плейтест с провайдером намеренно не запускался в рамках локального рефакторинга.

Порядок: сначала защита данных, потом каркас сценариев, потом перенос.

1. **Хотфиксы поверх итерации 1** (не ждут новой архитектуры):
   1.1. дефект 2.1: UNIQUE-индекс + pause/уточнение перед созданием мира поверх
        воркспейса + ORDER BY в `world_workspace()`; тест на «создай мир в review»;
   1.2. дефект 2.2: rules/help-пропуск перед default REVISE в collecting;
   1.3. дефект 2.6: usage-подсказка для неполных известных команд;
   1.4. дефект 2.5: удалить (или легализовать) `/game prepare`, `/world generate`.
2. **Каркас сценариев**: `app/scenarios.py` — `ScenarioId`, `CommandId`, дескрипторы,
   `resolve_scenario(state) -> Scenario` (расширение ModeRouter). Табличные тесты
   «состояние → сценарий».
3. **Стейт-модель**: генерация output-схемы из `llm_commands`, промпт, манифест из
   дескриптора; поднять `recent_chat_messages`; телеметрия
   `decision source=explicit|llm command=... scenario=...`.
4. **Перенос сценариев по одному**, начиная с самого дефектного:
   WORLD_EDITING_* → WORLD_SELECTION → PLAY_PENDING → PLAY → PREPARATION.
   На время переноса `decide()` остаётся для непереведённых сценариев (feature-флаг
   по ScenarioId), тесты итерации 1 продолжают охранять их.
5. **Демонтаж**: удалить `decide()`-цепочку, Левенштейн, `PHRASES`-словарь,
   `match_information_intent`, legacy-обёртки в `MessageApplication`; сюда же
   заложить отложенный шаг 4 итерации 1 (распил обработчиков в `app/handlers/`),
   т.к. таблица команд естественно расщепляется по сценариям.
6. **Приёмка**: плейтест на cheap-tier модели (grok-4.1-fast) по чек-листу:
   витиеватый запрос листа персонажа в PLAY; «покажи миры» внутри редактора;
   вопрос по правилам в collecting; «создай новый мир» при открытом review;
   ответ «да» при pending + сторонний вопрос при pending.

## 5. Анти-дрейф (дополнение к правилу итерации 1)

Любой фикс маршрутизации допустим только как:

1. фраза в `explicit_commands` конкретного сценария + табличный тест;
2. команда в `llm_commands` сценария + строка в COMMAND_TABLE + тест;
3. правка промпта стейт-модели + тест на её решение (мок-комплишн);
4. изменение дерева `resolve_scenario` + обновление этого документа.

Глобальные матчеры, нечёткие пороги и проверки до определения сценария — запрещены;
отклонять на ревью.
