# Ревью миграции на сценарный роутинг (итерация 2)

> Статус: ревью выполнено 2026-07-14 по состоянию рабочего дерева ветки `develop-v2`
> после миграции (`app/scenarios.py`, `app/dispatch.py`, `app/handlers/*`,
> `pipelines/state_decision.py`). Проверка: чтение кода, 174 зелёных теста, ruff чистый,
> прогон краевых сценариев через `decide()`/`match_explicit` напрямую.
>
> Статус исправлений 2026-07-14: замечания 2.1–2.4 закрыты. STATE-контекст и глубина
> истории строятся из дескриптора сценария; slash-команды исполняются по `CommandId`,
> известный root с неверными аргументами даёт usage; pending наследует информационные
> команды; настройки мира рендерятся вместе с provenance. Дублирующий guard создания
> мира теперь выводится из explicit-лексикона.
> Предыдущие документы: `dispatch-refactoring-plan.md`,
> `dispatch-v2-review-and-scenario-routing.md`.

## 1. Что сделано хорошо

Миграция выполнена по плану и без имитации:

- **Инверсия достигнута.** `resolve_scenario(state) -> Scenario` вызывается первым,
  ни один текстовый матчер не работает до определения сценария. Дерево состояний
  покрывает и pending-подвиды (`PLAY_PENDING_POOL/NARRATION/OTHER`), и `ROLL_RESUME`.
- **Закрытое пространство решений реализовано правильно.** `state_decision_type()`
  генерирует Pydantic-контракт с `Literal[...]` из `llm_commands` сценария — модель
  физически не может вернуть команду вне сценария; общий post-gate демонтирован.
- **Левенштейн и глобальный `PHRASES`-словарь удалены**; лексиконы точного совпадения
  живут в дескрипторах; per-scenario значение фразы работает (есть тест: «что ты
  умеешь» → каталог в выборе мира, справка в игре).
- **`SHOW_RULES`/`SHOW_HELP`/`CLARIFY` во всех интерактивных сценариях по построению**
  (закреплено тестом) — дефекты 2.2–2.4 прошлого ревью закрыты структурно.
- **Fallback на невалидное решение стейт-модели** (`PipelineValidationError` →
  `scenario.fallback` + warning-лог) — система не падает из-за кривого JSON
  классификатора.
- **Хотфиксы защиты данных выполнены**: UNIQUE partial index
  `one_active_world_project_per_channel`, guard `world_workspace_active` и в `decide()`
  (по фразам создания мира при открытом воркспейсе), и в
  `_handle_natural_world_creation` (defense in depth), детерминированный `ORDER BY`
  в `world_workspace()`. Голый `/advance` снова даёт usage. `/game prepare` и
  `/world generate` удалены из обработчика.
- **Распил бог-объекта**: `message_handler.py` — 145-строчный composition root;
  обработчики разнесены по `app/handlers/{dispatching,world_management,preparation,
  information,play,commands,support}`. Телеметрия `scenario_decision ... scenario=...
  command=... source=... gate=...` на месте.

## 2. Претензии

### 2.1. [СРЕДНИЙ] `context_projections` и `recent_chat_messages` дескриптора — мёртвые поля

Дескриптор `Scenario` объявляет per-scenario контекст
(`world_catalog`, `current_scene`, `actor_character`, глубину чата), но **ни одно из
этих полей нигде не потребляется** (единственные вхождения — сами объявления в
`scenarios.py`). `DispatchExecution` собирает контекст стейт-модели статичным
манифестом `INTENT_CLASSIFICATION` (`mode`, `scenario`, `pending_interaction`,
`world_workspace`; чат = 6 глобально).

Последствия:

- `SELECT_WORLD`: модель должна выбрать мир и вернуть `argument`, **не видя каталога
  миров** — аргумент извлекается только из формулировки игрока. «Выбираем второй»
  или «давай тот, что про болота» нерешаемы; спасает только нечёткий
  `_match_world_selection` по аргументу.
- `PLAY`: различение `DECLARE_ACTION` / `PLAYER_NARRATION` / `ASK_SCENE_QUESTION`
  происходит без сцены и листа персонажа, хотя дескриптор их запрашивает.
- Per-scenario глубина чата (6 для PLAY, 0 для ROLL_RESUME) игнорируется.

Требование: собирать манифест стейт-модели из дескриптора (динамический
`ContextManifest` или параметризация `manifest_for`), поставщики проекций —
по ключам `context_projections`. Тест: для каждого сценария проекции из дескриптора
присутствуют в `dynamic_context`.

### 2.2. [СРЕДНИЙ] Slash-команды: лексикон гейтит, но исполняет legacy-таблица

`decide()` при совпадении slash-команды возвращает
`RunHandler(HandlerKind.COMMAND, matched_command)`, но `matched_command` дальше
телеметрии не идёт — исполняет старый `_handle_command` со своим собственным
разбором. Снова две таблицы с ручной синхронизацией, и они уже разъехались:

- `/game scene` и `/character place` реализованы в `_handle_command`, но
  отсутствуют в лексиконах всех сценариев → **недостижимы** (не блокер: `start_game`
  сам создаёт сцену и размещает персонажей, — но тогда это мёртвый код);
- `unknown_command` в i18n рекламирует `/game prepare`, `/game scene`,
  `/character place` — команды, которые нельзя вызвать; `world_usage` упоминает
  удалённый `/world generate`; ключ `game_prepare_usage` осиротел;
- `/advance teleport` → `Reject("unavailable_play")` — ложное сообщение «недоступно
  в режиме» для известной команды с неверными аргументами (usage-фикс сделан только
  для форм, попадающих в лексикон).

Требование: единственный источник — `slash_commands` сценария; маппить
`CommandId` → конкретный обработчик (как для фраз), `_handle_command` разбить на
per-command функции; i18n-справку генерировать из лексиконов или вычистить вручную;
неверные аргументы известной команды → usage, не «unavailable».

### 2.3. [НИЗКИЙ] Pending-сценарии потеряли slash-команды

У `PLAY_PENDING_*` `slash_commands={}` → `/game status` или `/help @friend` при
открытом pending → `Reject("unavailable_play")`. В прошлой версии команды работали
при pending. Игрок, зависший на подтверждении пула, не может даже посмотреть статус.
Требование: унаследовать информационные slash-команды PLAY в pending-сценариях
(и, вероятно, добавить `SHOW_SCENE`/`SHOW_GAME_STATUS`/`SHOW_XP` в их `llm_commands`,
где сейчас только `ANSWER_PENDING`, `SHOW_CHARACTER_SHEET`, rules/help/clarify).

### 2.4. [НИЗКИЙ] `SHOW_WORLD_SETTINGS` не показывает настройки

`StateResponseKind.WORLD_STATUS` возвращает локализованную фразу «выше показаны все
настройки» без самих настроек (унаследовано, но теперь это явная InfoCommand —
контракт «рендер из стейта» нарушен). Требование: рендерить
`workspace["settings"]` + `sources`.

### 2.5. [КОСМЕТИКА]

- `WORLD_CREATION_PHRASES` в `scenarios.py` дублирует фразы `создай мир...` из
  explicit-лексикона WORLD_SELECTION — два места для одного словаря; guard в
  `decide()` мог бы опираться на лексикон.
- `DispatchSnapshot.mode_reason`/`game_id`/`locale`/`author_id` в `decide()` не
  используются (нужны только исполнителю) — снапшот шире решения; не ошибка, но
  контракт стоит сузить или задокументировать.
- `tests/test_dispatch.py`/`test_deterministic_intents.py` частично тестируют
  сценарные сущности под старыми именами файлов — переименовать при следующей уборке.

## 3. Вердикт

Архитектурная цель итерации 2 достигнута: сценарий — первоклассная сущность,
пространство решений закрыто per-scenario, глобальные матчеры демонтированы, данные
защищены. Претензии 2.1 и 2.2 — это «доделать декларативность до конца»: сегодня
дескриптор сценария честно описывает команды, но лишь наполовину описывает контекст и
вообще не управляет исполнением slash-команд. Пока эти два зазора открыты, у Кодекса
снова есть места для точечных заплаток (вторая таблица команд, статичный манифест).

Рекомендованный порядок: 2.1 → 2.2 → 2.3 → 2.4.
