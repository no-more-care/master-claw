## 2. Готовность к переключению языков

**Вывод: не готово. LLM-слой локализован, детерминированный слой — нет.**

`GameState.locale` валидируется как `{"ru", "en"}` (`app/game_service.py:46`) и реально
прокидывается в контекст пайплайна нарратива (`"session_brief": {"locale": game.locale}`,
`message_handler.py:707`) — модель действительно получает инструкцию писать прозу на нужном языке,
и это единственное место, где локаль на что-то влияет.

Всё остальное — весь код-рендеринг из `response_format.py` (`format_pool_confirmation`,
`format_roll_result`) и **все 811 строк** `message_handler.py` (командные ответы, ошибки валидации,
подсказки по синтаксису команд, `/game status`, `/character status`, `/xp status`) — это
захардкоженные русскоязычные строки без единого условия на `locale`. Проверка:
`grep -c '[а-яА-Я]' message_handler.py` → 96 строк с кириллицей, ни одна не ветвится по языку. Из
всего приложения ровно **одно** место действительно проверяет `game.locale == "ru"` —
fallback-фраза при падении пайплайна нарратива (`message_handler.py:735-739`).

Практическое следствие: если оператор поднимет `/game prepare ... en`, англоязычная группа
получит английскую прозу от LLM, но все механические сообщения ("🎲 **Пул: 2 куб.**", "Сколько
кубов добавить из запаса?", "Персонаж не создан: ...", тексты всех slash-команд) останутся на
русском. `locale` сейчас функционально — это переключатель языка **только для одного из восьми
пайплайнов**, а не переключатель языка игры.

Раньше эту роль выполняли `locales/{ru,en}/templates/*.md` (v1) — `docs/v2-discord-formatting.md`
прямо говорит, что v2 "reuses the useful parts of the legacy locale templates, but renders them in
code instead of asking an LLM" — но фактически перенесена и адаптирована в код была только русская
версия. Если английский — не просто теоретическая опция, а реальный сценарий использования,
`response_format.py` и командные ответы `message_handler.py` нужно параметризовать по `game.locale`
(например, словарь шаблонов на язык, как это уже сделано для одной fallback-фразы) до реального
теста с англоязычной группой.

## 3. Состояние мира и персонажей

### 3.1 Что устроено корректно

- `WorldState`/`GameState`/`CharacterState`/`Scene` — везде optimistic concurrency через
  `expected_revision`, подтверждено тестами конфликтов ревизий
  (`test_scene_projection.py`/`test_character_storage.py` из первого коммита, не менялись).
- LLM предлагает только *патч* (`SceneConsequencePlan.add_facts/remove_facts`), код применяет его
  транзакционно с проверкой ревизии сцены (`apply_scene_patch`) — модель не может тихо переписать
  состояние сцены.
- `docs/data-model.md` (новый) — честное и точное описание агрегатов, стоит держать актуальным как
  единственный источник правды по схеме БД вместо вычитывания `sqlite.py` построчно.

### 3.2 Генерация мира всё ещё не секционная — открытый пункт с первого ревью

План (`openhands-refactoring-plan.md`, §6.2) явно требует: "Генерация выполняется секционно:
outline -> structured sections -> cross-reference validation -> consistency critic -> publish. Один
огромный вызов «создай весь мир» не используется." В реализации `/world generate` вызывает
`self._worldgen_pipeline.run(...)` **один раз** с `target_section: "full_initial_draft"`
(`message_handler.py:264-282`) — весь мир (премиса, темы, локации, фракции, напряжения, секретный
сюжет) генерируется одним вызовом `WorldDraft`, без outline-этапа и без consistency-critic прохода.
Название `PipelineName.WORLD_SECTION` и параметр `target_section` намекают на секционность, которой
в реализации нет — это не менялось с первого ревью (`git diff c6da00e -- pipelines/worldgen.py` —
пусто). Для маленьких миров это может быть приемлемым упрощением, но при росте промпта (много
локаций/фракций одним вызовом) это первый кандидат на потерю согласованности и на превышение
`input_token_budget`/`output_token_budget` (сейчас 16000/2400 токенов на весь мир сразу).

### 3.3 История чата для промптов не изолирована по сцене/игроку

`SQLiteStore.recent_chat_messages` (`storage/sqlite.py:945-968`) при вызове с `channel_id` (а
`_assemble_context` почти всегда передаёт оба — `game_id` и `channel_id`) фильтрует **только по
Discord-каналу**, независимо от того, какой игрок или какая сцена в него писали:

```python
if channel_id is not None:
    where = "messages.channel_id = ?"
```

Архитектура прямо поддерживает несколько независимых сцен в одном канале одной игры (план, §17
п.7). Это не утечка приватности в строгом смысле — все игроки и так видят все сообщения в общем
Discord-канале, — но это шум в промпте: интерпретация действия игрока A (`ACTION_INTERPRETATION`,
бюджет 2 последних сообщения) может получить в контекст последние реплики игрока B из другой сцены,
не относящиеся к текущему действию. Раздел 5.2 плана описывает `session_brief`/`scene_neighborhood`
как выборки, специфичные для текущей сцены — сейчас chat-история этому требованию не соответствует.
Стоит либо фильтровать `recent_chat_messages` по автору/сцене, когда сцен в канале больше одной,
либо явно задокументировать, что история — общеканальная по замыслу.

## 4. Промт-билдинг

Контракт (`docs/llm-pipeline-contract.md`) реализован дословно: `system` (роль + инварианты +
`rule_fragments`, помечен `cache_prompt=True`) → `user: DYNAMIC CONTEXT` (state-проекции +
usqlite-history) → `user: CURRENT TASK` → typed output через `native_tool` или `prompt_json`
(`adapters/openhands.py:74-108`, `pipelines/base.py`). Порядок разделов детерминирован, что
действительно позволяет провайдерским prefix-кэшам работать — это прямо подтверждено
`cache_read_tokens`/`cache_write_tokens` полями в телеметрии.

Два момента, которые стоит проговорить:

1. **Версионирование фрагментов исчезло.** В `prompts/manifest.json` больше нет поля `"version"`
   на фрагмент (было в первой реализации, теперь `AssembledContext.fragments` хранит только
   `id`, без версии). План (§7.3) требовал `id`, `version`, `scope`, `dependencies` на каждый
   fragment для регрессионного тестирования промптов. Сейчас изменение текста
   `prompts/rules/*.md` никак не видно в телеметрии/аудите вызова — раньше можно было бы связать
   конкретный LLM-звонок с конкретной версией правила, теперь только с его id. Небольшая потеря
   относительно плана, но воспроизводимость промпт-аудита от неё страдает.
2. **Оценка токен-бюджета остаётся эвристикой `len/4`** (`assembler.py`, `estimated_tokens`) — не
   привязана к токенизатору конкретной модели. Для `nex-n2-mini`/`gpt-5.6-luna` с их узкими
   бюджетами (2500/300 у intent-классификации) это не критично, но при добавлении моделей с другими
   токенизаторами (не BPE-совместимыми с грубой оценкой) budget-gate может как ложно ронять валидные
   запросы, так и пропускать реально слишком длинные.

## 5. Фаллбэки — неравномерное покрытие, один системный пробел

Явный, протестированный fallback в проекте **один**: если `narrative_pipeline` падает после провала
одной попытки repair, `_render_roll_outcome` ловит исключение и подставляет заранее заданную фразу
на языке игры (`message_handler.py:723-739`). Это единственное место в приложении с таким
поведением.

Все остальные вызовы LLM-пайплайнов — `intent`, `action`, `consequence`, `player_narration`,
`advancement_safety`, `character_creation`, `worldgen` — **не обёрнуты** в try/except на уровне
`message_handler.py`/`advancement_coordinator.py`. `PipelineValidationError` (или любая сетевая
ошибка) после провала единственного repair-запроса поднимается до
`ChannelOrchestrator.process_available`/`process_until_quiet`, батч помечается `fail_batch(retry=True)`,
и только после исчерпания ретраев игроку уходит общая нотификация "Не удалось обработать запрос...".

Самый чувствительный случай — `_render_roll_outcome` (`message_handler.py:664-739`): для
GM-исходов (`gm_success`/`gm_failure`) метод сначала (без try/except) вызывает
`_ensure_scene_consequence` (строка 688) и только потом, в защищённом блоke, — нарратив. Бросок к
этому моменту уже **необратимо закоммичен** в `rolls` (immutable row), а строка `mechanical`
(результат броска — то, что игрок ждёт увидеть немедленно) уже посчитана на первой строке функции.
Если пайплайн `consequence` начнёт стабильно фейлиться на конкретной сцене (например, модель не
укладывается в схему `SceneConsequencePlan` из-за необычного состояния сцены), игрок не увидит даже
уже состоявшийся результат броска — вся обработка уйдёт в retry/dead-letter, а `mechanical` будет
потерян при каждой попытке, потому что функция ни разу не доходит до `return`. Ретраи здесь
идемпотентны по состоянию (`has_scene_patch` не даст применить патч дважды), но не идемпотентны по
пользовательскому опыту — сообщение не дойдёт, пока пайплайн `consequence` не начнёт отвечать.

**Рекомендация:** дать `_render_roll_outcome` собственный safe-fallback вокруг
`_ensure_scene_consequence`, симметричный уже существующему вокруг нарратива — если планирование
последствий падает, вернуть `mechanical` сразу (без патча сцены, его можно доприменить при
следующем успешном вызове/ручной команде), а не терять уже подтверждённый результат броска. Это
прямое следствие «Fail closed» из плана (§2 принцип 7) — сейчас fail closed работает только для
записи состояния, но не для доставки уже готового ответа игроку.

## 6. Читаемость и модульность

С первого ревью — не улучшилось, слегка выросло:

| Файл | Было (первое ревью) | Сейчас |
|---|---:|---:|
| `app/message_handler.py` | 772 строки | 811 строк |
| `storage/sqlite.py` | 1494 строки | 1508 строк |

`message_handler.py` — по-прежнему один класс `MessageApplication`, совмещающий диспетчеризацию,
разбор всех slash-команд (`/world`, `/game`, `/character`, `/xp`, `/advance`, `/help`), обработку
декларации действия, рендер исхода броска и сборку контекста (`_assemble_context`). Тестовое
покрытие подтверждает это как узкое место: `pytest --cov` показывает 72% на этом файле (самое
низкое среди `app/*`) — непокрыты в основном как раз ветки командного парсера (строки 251-320,
417-508 и т.д.), то есть именно там, где рост файла продолжается быстрее всего.

`storage/sqlite.py` — 87% покрытия, но по-прежнему один класс на все агрегаты. Не блокер (SQLite,
один воркер — осознанное решение владельца), но по мере добавления команд оба файла продолжат расти
в одном месте. Стоит запланировать разбивку `MessageApplication` на per-command handlers (или хотя
бы per-domain group: world/game/character/advancement) при следующей заметной итерации — сейчас
это не мешает, но откладывать дальше будет дороже.

Отдельно, некритично: `adapters/discord_bot.py` и `cli.py` имеют **0% покрытия тестами** (см. отчёт
`pytest --cov` — `discord_bot.py 0/63`, `cli.py 0/107`). Домен и оркестрация тестируются хорошо;
тонкий Discord-адаптер и CLI — нет вообще. Для `cli.py` это в основном не страшно (аргументы
`argparse` + вызов уже протестированных сервисов), но `discord_bot.py` содержит нетривиальную
логику дебаунса и пере-планирования задач (`_process_after_debounce` в `on_ready`/`on_message`/
`_publish_outbox`), которая ни разу не проверена — даже с моком `discord.Client`.

## 7. Согласованность терминов между инструкциями

### 7.1 [Важно] Семантика уровней `narrator_rights_level` определена только в архивном v1-документе

`domain/state.py` определяет `NarratorRightsLevel = {disabled, minor, significant, madness}`, и это
значение реально попадает в промпт (`"narrator_rights_level": game.narrator_rights_level.value`,
`message_handler.py:717`). Но что именно разрешено на уровне `significant` в отличие от `minor` или
`madness` — **нигде в v2-материале не описано**. Единственное существующее объяснение — раздел
"11b. NARRATOR RIGHTS — LEVELS" в архивном `skills/rules/SKILL.md` (v1), который сам `CLAUDE.md`
теперь явно помечает как "archived v1 reference material, not the runtime architecture". Живой
промпт-фрагмент `prompts/rules/narrator_rights.md`, который реально подключён к пайплайнам
`OUTCOME_NARRATION` и `PLAYER_NARRATION_REVIEW`, содержит только одно предложение про сам факт
существования прав ("Narration must stay within the supplied rights") — без определения диапазона
дозволенного на каждом уровне. Модель, проверяющая нарратив игрока
(`PlayerNarrationReview.accepted`), сейчас вынуждена либо угадывать смысл `significant`/`madness` по
названию, либо (что хуже) молчаливо использовать какую-то собственную трактовку — то самое
поведенческое дрожание между сессиями/моделями, ради устранения которого затевался переезд на v2.
**Рекомендация:** перенести определения уровней из `skills/rules/SKILL.md` §11b в
`prompts/rules/narrator_rights.md` (в сжатом виде, как остальные rule-фрагменты) прежде чем
полагаться на `significant`/`madness` в реальной игре.

### 7.2 [Мелкое] Значение `narrator_rights="gm_automatic"` не входит в типизированный словарь

`NarratorRights` (`domain/mechanics.py:13-17`) — типизированный enum ровно с 4 значениями:
`player_success`/`gm_success`/`player_failure`/`gm_failure`. Но при обработке действий без броска
(`ActionResolution.AUTOMATIC`) в контекст пайплайна `consequence` передаётся пятое, нигде не
объявленное значение — литеральная строка `"gm_automatic"`
(`message_handler.py:569`, продублировано в `model_smoke.py:33`). Оно не ломает типизацию (поле
`outcome_source`/`narrator_rights` в `SceneConsequencePlan`-контексте — обычная строка, не enum), но
это ровно тот вид «параллельной терминологии», который стоит либо формализовать (добавить как
пятое значение в `NarratorRights` с пометкой "no roll" в документации), либо явно задокументировать
рядом с остальными в `prompts/rules/narrator_rights.md`/`docs/data-model.md` — сейчас человек,
ищущий полный список возможных значений `narrator_rights` по `NarratorRights`-enum, этого значения
не найдёт.

### 7.3 [Мелкое] Одно и то же понятие «декларация действия» называется по-разному в русском UI

`message_handler.py:517` — "Обработка игровых **деклараций** ещё не настроена"; тот же концепт в
той же функции на строке 618 — "Уточните **заявку**" (после провала валидации пула). Оба сообщения
относятся к одному домен-понятию (`declaration`/`ActionInterpretation`), но используют разные
русские существительные. Не мешает работе, но стоит унифицировать при следующей правке текстов
(например, оставить «заявка» как игровой термин, «декларация» — только как английское имя поля в
логах/коде).
