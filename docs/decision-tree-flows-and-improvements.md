## 1. Правила игры → обязанности мастера

BlackBirdPie — нарративная система с жёсткой лёгкой механикой:

- пул = +1 куб за каждую применимую черту/аспект/флаг (макс. 1 флаг) + резерв;
- бросок Nd6, 4–6 = успех; сложность 2–7;
- права нарратора: успехи > сложности → игрок («да, и…»), = → мастер («да, но…»),
  = сложность−1 → игрок («нет, но…»), меньше → мастер («нет, и…»);
- резерв 7 макс.: при успехе потрачен, при провале возвращается +1;
- помощь = 1 куб от другого игрока, без броска;
- лист персонажа — закон (18 очков черт, аспекты = уровню, ≥3 флага);
- опыт ~1/30 минут игры; повышение N→N+1 стоит N.

Из правил вытекают обязанности мастера, и в v2 они **разделены между кодом и LLM**:

| Обязанность мастера за столом | В v2 исполняет |
|---|---|
| честный бросок | код (`ActionService`, RNG) — LLM не видит кубы до результата |
| подсчёт пула, лимиты флагов/резерва | код (`domain/mechanics.py`, `MechanicsError`) |
| определение сложности и применимости черт | LLM REASONING (`ACTION_INTERPRETATION`) — **единственное место, где LLM судит по правилам** |
| «жди подтверждения перед броском» | код (pending `pool_confirmation`) |
| раздача прав нарратора | код (формула) |
| нарратив исхода | LLM NARRATIVE (`OUTCOME_NARRATION`, + review) |
| проверка наррации игрока на превышение прав | LLM REASONING (`PLAYER_NARRATION_REVIEW`) |
| память сцены (мёртвый NPC мёртв) | код (scene facts) + LLM REASONING (`CONSEQUENCE_PLANNING` — минимальный патч фактов) |
| восстановление резерва (отдых/награда за отыгрыш) | LLM REASONING (`RESERVE_RECOVERY`) + код применяет |
| понимание, чего хочет игрок | лексикон (0 LLM) → LLM STATE (`StateDecision`) |
| беспристрастность («не снижай сложность по просьбе») | архитектурно: игрок не может повлиять на пул/бросок иначе как через код |

Ключевой принцип уже соблюдён: **LLM решает и описывает, но никогда не считает и не
бросает**. Это главное отличие от табличного v1, где модель могла сфабриковать бросок
(см. baseline в CLAUDE.md — 3 из 4 дешёвых моделей фабрикуют).

## 2. Каталог флоу одного сообщения

Обозначения стоимости: `0` — без LLM; `S` — STATE (дёшево, без размышлений);
`R` — REASONING; `N` — NARRATIVE.

### 2.1. Определение сценария (всегда, 0 LLM)

```
resumed_roll (по event_id) ─────────────→ ROLL_RESUME
workspace collecting/review ────────────→ WORLD_EDITING_*
game нет ───────────────────────────────→ WORLD_SELECTION
lifecycle draft/preparing ──────────────→ PREPARATION
pending pool/narration/other ───────────→ PLAY_PENDING_*
lifecycle active ───────────────────────→ PLAY
```

### 2.2. Флоу по сценариям

**WORLD_SELECTION**: явная фраза/`/world create` → `0`; иначе `S` →
{каталог `0` | выбор мира → prepare_game `0` | создание мира → intake `R` →
воркспейс | rules `R` | help `0` | clarify `0`}.

**WORLD_EDITING_COLLECTING/REVIEW**: явные контролы (сгенерируй/подтверждаю/выйти/
настройки) → `0`; иначе `S` → {ревизия `R` | генерация `R×N секций` | подтверждение
`0` | выход `0` | rules/help/clarify}. Fallback collecting = REVISE (осознанно),
review = CLARIFY (черновик не портится молча).

**PREPARATION**: slash-команды и явные фразы → `0`; `/character create` → `R`
(черновик персонажа) + валидация кодом (18 очков и т.д. — `character_invalid` при
нарушении); иначе `S` → {создание/выбор персонажа, старт, конфигурация `R`, статусы
`0`}.

**PLAY, информационные запросы**: «покажи персонажа», «что вокруг», `/game status` →
`0` (лексикон). Перефразированные («как там мой перс?») → `S` → `SHOW_*` → рендер
кодом `0`. Это соответствует принципу «не запускать думающую модель, когда игрок
просил лист персонажа»: худший случай — один дешёвый STATE-вызов.

**PLAY, заявка действия** (полный жизненный цикл, 2+ сообщения игрока):

```
заявка → S (DECLARE_ACTION) → R (интерпретация: черты/аспекты/флаг/сложность)
  ├─ CLARIFICATION → уточняющий вопрос игроку           [S+R, тупика нет]
  ├─ AUTOMATIC     → R (consequence) [+ N (нарратив)]   [обыденное действие без броска]
  └─ ROLL → MechanicsError? → «пул некорректен» иначе pending pool_confirmation
подтверждение: «да»/«нет»/число → 0;  вольный текст → R (ROLL_CONFIRMATION)
  → бросок 0 → права 0
  ├─ права у игрока → pending player_narration
  │    → текст игрока → S (ANSWER_PENDING) → R (review прав)
  │       ├─ принято → R (consequence) → публикация в narrative-канал
  │       └─ превышение → просьба смягчить (pending остаётся)
  └─ права у мастера → R (consequence) → N (нарратив) [+ review R] → R (резерв)
```

Полный ход = 4–7 LLM-вызовов на 2–3 сообщения игрока — приемлемо, потому что
дорогие роли включаются только после того, как дешёвые слои сузили задачу.

**PLAY_PENDING_***: да/нет/число → `0`; иначе `S` (модель видит текст pending и
решает: это ответ или сторонняя просьба) → `ANSWER_PENDING` | `SHOW_*` | clarify.

### 2.3. Насколько дерево проходит по этим флоу

Хорошо: happy-path всех сценариев покрыт; тривиальные запросы дёшевы; заявка
защищена подтверждением; идемпотентность (has_scene_patch по causation_id,
UNIQUE pending на игрока, идемпотентный outbox) позволяет безопасный повтор.

Слабые места — не в маршрутизации, а в **обработке отказов** на дорогих участках
(раздел 3) и в **тупиках последовательностей** (раздел 4).

## 3. Точки отказа в baseline 2026-07-14

Таблица ниже фиксирует исходное состояние на момент исследования и не описывает
текущий runtime. Актуальный статус исправлений приведён во вводном блоке выше и в
`v2-implementation-status.md`. В baseline inbox использовал `attempts >= 3 → failed`;
`PipelineValidationError` завершался терминально без ретраев, а игрок получал
`system_failure`. Внутри пайплайна выполнялись 1 попытка + 1 schema-repair.

| # | Отказ | Baseline на 2026-07-14 | Оценка baseline |
|---|---|---|---|
| A | стейт-модель вернула невалидное решение | `scenario.fallback` (clarify/revise) | ✅ образцово |
| B | нарратив упал после броска | `narrative_fallback`, механика доставлена | ✅ |
| C | consequence упал после броска | вернуть механику без патча сцены | ✅ |
| D | reserve recovery упал | проглочен, логируется | ✅ |
| E | **интерпретация заявки (`ACTION_INTERPRETATION`) невалидна после repair** | `PipelineValidationError` → терминально → `system_failure` | ❌ игрок сделал осмысленную заявку и получил «системный сбой»; правильный ответ — `clarify_action` |
| F | **создание персонажа / world intake / advancement intake / NL-подтверждение броска невалидны** | то же: `system_failure` | ❌ то же самое |
| G | **превышение бюджета контекста (`ContextAssemblyError`)** | 3 ретрая **идентичной** детерминированной ошибки → `system_failure` | ❌ ретраи бессмысленны; «нехватка токенов» — банальная ошибка, требующая деградации, а не отказа |
| H | транзиентная ошибка провайдера (сеть/429/5xx) | 3 ретрая всего батча без backoff | ⚠️ ретраи есть, но немедленные — при недоступности провайдера сгорают за секунды |
| I | **один сбойный обработчик в батче** | `fail_batch` помечает **все** сообщения батча; уведомление о сбое всем | ❌ сообщение игрока Б падает из-за заявки игрока А |
| J | pending завис (игрок ушёл) | pending вечен; перехватывает сценарий игрока | ⚠️ «отмена» спасает, но игрок должен догадаться; напоминания/TTL нет |
| K | `FallbackCompletionPort` (запасная модель) | есть в конструкторе портов | ⚠️ покрывает не все роли; политика подключения не задокументирована |

Строки E–G были прямым нарушением целевого принципа: системное сообщение об ошибке
возникало там, где достаточно уточняющего вопроса или урезанного контекста.

## 4. Исторический план улучшений

Приоритет: П1–П3 — устойчивость (убирают `system_failure` из штатных сценариев);
П4–П5 — качество взаимодействия; П6–П7 — эксплуатация и эволюция.

### П1. Fallback-команда в манифесте каждого пайплайна

Расширить `ContextManifest` полем `on_invalid: FallbackAction` и обрабатывать
`PipelineValidationError` на месте вызова, а не в оркестраторе:

| Пайплайн | on_invalid |
|---|---|
| ACTION_INTERPRETATION | `clarify_action` («не понял заявку — что именно делает персонаж и чем?») |
| CHARACTER_CREATION | просьба переформулировать бриф (1–2 предложения о персонаже) |
| WORLD_INTAKE | просьба переформулировать описание мира |
| ADVANCEMENT_INTAKE | показать доступные повышения + usage |
| ROLL_CONFIRMATION | `reserve_usage` (ответ «да», «нет» или число резерва) |
| PLAYER_NARRATION_REVIEW | принять наррацию с пометкой «без проверки прав» ЛИБО попросить повторить — выбрать при реализации (консервативно: попросить повторить) |
| OUTCOME_NARRATION / CONSEQUENCE / RESERVE_RECOVERY | уже деградируют — формализовать в манифесте |
| StateDecision | уже `scenario.fallback` |

Критерий: `PipelineValidationError` никогда не доходит до оркестратора из штатного
флоу; `system_failure` остаётся только для настоящих инвариантных багов.

### П2. Таксономия ошибок и политика ретраев в оркестраторе

Ввести классификацию вместо бинарного `isinstance(PipelineValidationError)`:

- **Deterministic** (`ContextAssemblyError`, `MechanicsError` вне обработчика,
  программные баги-инварианты): ретраев нет — результат не изменится;
- **Transient** (таймаут/сеть/429/5xx от провайдера — нужен свой exception-тип в
  адаптере OpenHands): ретрай с экспоненциальным backoff (например 5с/30с/2м),
  а не мгновенный; между попытками сообщение остаётся pending;
- **Schema** (`PipelineValidationError`): не должна долетать (П1); если долетела —
  терминально с алертом.

Плюс **изоляция сообщений в батче**: `SequentialBatchProcessor` обрабатывает
по одному — сбой N-го сообщения должен фейлить только его, успевшие ответы
доставляться, остальные возвращаться в pending. Сейчас `fail_batch` валит весь claim.

### П3. Лестница деградации контекста вместо `ContextAssemblyError`

`ContextAssembler.assemble` при превышении бюджета должен не бросать исключение, а
резать контекст по приоритету (и логировать факт деградации):

1. chat_messages → до 1;
2. domain_events → до 1;
3. длинные строковые поля проекций (описание сцены, факты) → усечение с маркером;
4. только если и это не влезло — ошибка (уже Deterministic, без ретраев, с
   человеческим ответом «слишком длинное сообщение, сократите» для случая, когда
   бюджет съел сам ввод игрока).

Отдельно: входное сообщение игрока > N символов — усекать/отклонять до сборки
(«слишком длинно для одной заявки, разбей на части»), чтобы бюджет не взрывался
предсказуемым способом.

### П4. Дожать декларативность сценария (из ревью, претензии 2.1–2.2)

- собирать манифест стейт-модели из `context_projections`/`recent_chat_messages`
  дескриптора: каталог миров для `SELECT_WORLD`, сцена+персонаж для PLAY;
- slash-команды исполнять по `CommandId` из лексикона, а не второй таблицей;
- вернуть информационные команды в pending-сценарии (см. претензию 2.3).

### П5. UX отказов и тупиков

- **Каждый Reject/CLARIFY — с подсказкой**: не «уточните», а «сейчас можно: …»
  (ключи `scenario_help_*` уже есть — переиспользовать в clarify);
- **`system_failure` дифференцировать по стадии**: если бросок уже совершён —
  «бросок сохранён (X успехов), опиши исход позже»; если нет — «заявка не обработана,
  повтори» (идемпотентность это уже позволяет: roll привязан к confirmation_event_id);
- **TTL/напоминание для pending**: при следующем сообщении игрока старше N часов —
  напомнить текст pending и предложить «отмена»; авто-отмена pool_confirmation по
  давности (наррация — не отменять, только напоминать);
- **`SHOW_HELP` в pending-сценариях** должен описывать pending («жду подтверждения
  пула: да / число резерва / отмена»), а не общий help игры.

### П6. Телеметрическая петля для лексикона

`routing-quality-report` агрегирует фразы, ушедшие в STATE и вернувшиеся
`SHOW_*`/`ANSWER_PENDING` с высокой уверенностью: нормализованная фраза, сценарий,
команда, частота и средняя уверенность. Observation ledger идемпотентен по Discord
event id, поэтому crash-replay не завышает частоту. Кандидаты попадают в
explicit-лексикон только после ручной проверки смысла, локали и конфликтов сценариев.
Тот же отчёт раздельно считает schema-repair rate, invalid-result rate и
secondary-model fallback rate с собственным знаменателем для каждого сигнала.
Еженедельный cadence и точные определения описаны в `performance-telemetry.md`.

### П7. Резервная модель и smoke-петля

- задокументировать и покрыть `FallbackCompletionPort` политику: для STATE —
  запасной той же роли; для REASONING — допустим апгрейд тира; NARRATIVE — можно
  деградировать в `narrative_fallback` без второй модели;
- `masterclaw model-smoke` расширить сценарной матрицей (по одному вызову на роль ×
  ключевые пайплайны), чтобы смена модели проверялась до деплоя.

## 5. Критерии готовности, использованные при внедрении

1. Ни один штатный флоу из раздела 2 не может закончиться `system_failure`:
   для каждой строки E–G из таблицы отказов есть тест «пайплайн вернул мусор дважды →
   игрок получил осмысленный ответ своего сценария».
2. Транзиентная недоступность провайдера на < 5 минут не приводит к потере сообщений
   и терминальным сбоям (тест с фейковым портом, падающим первые K вызовов).
3. Сбой обработчика одного сообщения не влияет на доставку ответов остальным
   сообщениям батча.
4. «Покажи персонажа» и его перефразировки стоят ≤ 1 STATE-вызова; полный ход заявки
   ≤ 7 LLM-вызовов (закрепить в perf-тесте по числу вызовов фейкового порта).
5. Плейтест на cheap-tier модели: сценарии-ловушки — сверхдлинная заявка, мусорный
   ответ на подтверждение пула, вопрос статуса при висящем pending, уход игрока на
   сутки с открытым pending.
