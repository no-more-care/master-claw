# MasterClaw v2 — план доведения runtime до полноценного игрового мастера

> Дата: 2026-07-16
> Основание: повторный анализ текущего рабочего дерева `develop-v2`.
> Цель: сохранить сильное детерминированное ядро, закрыть опасные ветви неоднозначности,
> подключить созданный мир к игровому мастеру и сделать последствия хода полноценным
> изменением канонического состояния.

## 1. Зафиксированные продуктовые решения

1. **Discord-упоминания игроков не добавляются к каждому ответу.**
   Они создают лишние уведомления и визуальный шум. Если в одном разговорном фрагменте
   участвуют несколько игроков и адресат без уточнения неочевиден, мастер использует
   **имя персонажа**, а не `<@player_id>`.
2. **Все персонажи начинают игру вместе.**
   Независимо от того, создан персонаж игроком или выбран из прегенов, при старте он
   помещается в общую стартовую сцену. Поле `home_location_id` у прегенов удаляется:
   оно не является частью требуемого продукта и не управляет размещением.
3. **Верхний режим и механика остаются code-owned.**
   LLM не получает права выбирать lifecycle, бросать кубы, менять резерв, обходить
   pending или напрямую писать SQLite.
4. **Свободный язык остаётся основным интерфейсом.**
   Slash-команды — диагностические и автоматизационные shortcuts, но не обязательный UX.

## 2. Целевой поток сообщения

```text
Discord event
  -> durable inbox / deduplication
  -> persisted mode + workspace + player pending
  -> scenario
  -> exact control / safe deterministic information
  -> bounded state decision or compound request plan
  -> command safety policy
  -> domain handler
  -> typed reasoning/narrative result
  -> deterministic validation and revision gates
  -> atomic canonical patch + domain events + outbox
```

## 3. Поток A — безопасность ветвления и pending

### A1. Политика безопасности команд

Добавить к сценарию явную политику выполнения:

- `read_only` — допускается при любом валидном typed-решении;
- `inferred` — допускается выше порога уверенности, иначе `CLARIFY`;
- `explicit_only` — только точная фраза или slash-команда.

К `explicit_only` относятся как минимум:

- публикация мира;
- запуск генерации/перегенерации;
- выход из редактора;
- запуск игры.

`confidence` модели перестаёт быть только телеметрией. Низкая уверенность не должна
приводить к изменению состояния. Невалидный state-result в collecting-сценарии должен
уходить в безопасное уточнение, а не автоматически дописывать brief.

### A2. Составные сообщения

Добавить typed-представление составного игрового запроса. Минимально поддержать:

- ролеплей/реплика + вопрос о сцене;
- ролеплей/реплика + заявка действия;
- вопрос + условная заявка действия.

План обязан сохранять порядок частей и не выполнять условную заявку до получения
ответа, если её условия ещё не установлены. Несовместимые или опасно неоднозначные
части приводят к одному конкретному уточняющему вопросу.

### A3. Pending как отдельная state machine

Для каждого pending-kind определить разрешённые операции:

- `ANSWER_PENDING`;
- `CANCEL_PENDING`;
- безопасные информационные команды;
- reminder/expiry policy.

Требования:

- stale narration/choice не блокирует все последующие сообщения;
- `отмена` отменяет любой отменяемый pending;
- отмена/expiry пула транзакционно возвращает все help dice;
- player-narration можно отменить без передачи слова «отмена» в review pipeline;
- пользовательский ответ после reminder всё равно обрабатывается.

## 4. Поток B — игровой GM-контекст и память

### B1. GM world projection

Игровые reasoning/narrative pipelines получают минимальную релевантную GM-проекцию:

- premise, themes, factions и tensions;
- secret plot только для GM-owned pipeline;
- текущую локацию и соседние/доступные направления;
- активные сюжетные нити, известные подсказки и угрозы;
- релевантные персонажи/NPC и их недавнюю память.

STATE-router не получает секретный сюжет, если он не нужен для выбора команды.

### B2. Имена персонажей и multiplayer

- scene projection содержит соответствие `player_id -> character name`;
- при нескольких одновременных адресатах модель получает прямую инструкцию различать
  их именами персонажей;
- рутинные ответы не получают Discord mention;
- play status panel строится относительно сцены текущего игрока, а не последней
  изменённой сцены всей игры.

### B3. Память ответов мастера

Существенные ответы мастера сохраняются как idempotent interaction/domain events:

- NPC/GM roleplay replies;
- принятая player narration;
- итоговая outcome narration или её компактное каноническое summary.

Последующие pipelines получают небольшой scene-local фрагмент этой истории. Outbox не
становится источником истины; canonical interaction event создаётся отдельно.

## 5. Поток C — полноценные последствия хода

Заменить `SceneConsequencePlan` на revision-bound `OutcomePatch`, способный выразить:

- add/remove scene facts;
- add/remove/reduce character conditions;
- add/remove plot items;
- перемещение персонажей между существующими сценами;
- создание минимального scene/NPC state, если это разрешено исходом;
- открытие/закрытие сюжетных нитей;
- допустимый narrator-rights reward.

### C1. Детерминированные ограничения

- модель может менять только перечисленные target ids;
- чужой PC не управляется без его заявки;
- перемещение проверяет принадлежность сцены игре;
- condition/item mutations проходят точные before/after checks;
- весь patch и domain event применяются атомарно;
- retry по одному causation id ничего не дублирует.

### C2. Права рассказчика

Поддержать минимум:

- `disabled` — никаких player-owned world mutations;
- `minor` — непосредственное описание + один допустимый малый reward;
- `significant` — разрешённые вторичные детали/NPC/items;
- `madness` — расширенный patch с сохранением hard limits.

Если выбран reward `remove_condition`, он применяется кодом. Будущие бонусы должны
иметь каноническое ограниченное представление и однократное детерминированное
потребление; если такое представление не реализовано, соответствующий reward нельзя
обещать игроку.

## 6. Поток D — миры и подготовка

1. Удалить `home_location_id` из схемы прегенов, генерационных промптов, проверок и тестов.
2. Оставить общее размещение всей группы в стартовой сцене.
3. Ограничить `specified_fields` перечислением реально поддерживаемых полей.
4. Перенести cross-reference/identity проверки `WorldDraft` в semantic validation,
   участвующую в bounded repair/fallback.
5. Ошибка генерации оставляет workspace целым и возвращает понятный retry/clarification,
   а не общий `system_failure`.
6. Синхронизировать документацию с фактически выбранным generation workflow.

## 7. Поток E — отказоустойчивость

- Любой уже применённый canonical patch должен иметь безопасный player-facing результат.
- Automatic action не может изменить сцену, а затем закончиться общим системным сбоем
  только из-за недоступной прозы.
- Pipeline-specific `on_invalid` применяется на всех вызовах, а не только на отдельных
  happy-path ветках.
- Semantic model error отличается от transient provider error и invariant bug.

## 8. Тестовая матрица приёмки

Обязательные новые тесты:

1. `confidence=0.01` не публикует мир и не запускает игру.
2. Неявная похвала review-драфта не считается подтверждением.
3. Составное сообщение не теряет вопрос или условную заявку.
4. Fresh/stale narration pending можно отменить.
5. Stale narration можно завершить нормальным ответом.
6. Help die возвращается при cancel и expiry.
7. Игрок в сцене B получает panel сцены B после изменения сцены A.
8. Два игрока различаются именами персонажей без Discord mentions.
9. GM помнит собственную предыдущую NPC-реплику.
10. Play pipelines получают релевантный secret/public world slice без утечки в
    детерминированный публичный status.
11. Outcome patch добавляет/снимает condition, выдаёт item и перемещает персонажа с
    проверкой revision.
12. Narrator-rights reward применяется ровно один раз.
13. Неизвестный `specified_fields` отвергается схемой.
14. Ошибка cross-reference получает bounded repair/fallback.
15. Narrative failure после automatic patch возвращает безопасный ответ.

Финальная проверка:

```bash
uv run python -m ruff check src tests
uv run python -m ruff format --check src tests
uv run python -m pytest --cov=masterclaw --cov-report=term-missing -q
uv run masterclaw doctor
```

## 9. Порядок интеграции

1. A: command safety + pending.
2. D: world schemas/validation и удаление `home_location_id`.
3. B: GM context, multiplayer projection и interaction memory.
4. C: расширенный OutcomePatch и narrator-rights rewards.
5. E: унификация fallback/partial-commit поведения.
6. Полная интеграционная проверка.
7. Повторный анализ архитектуры, дерева решений и неоднозначных сценариев.

## 10. Критерий завершения

Работа завершена, когда:

- штатная неоднозначность никогда не вызывает destructive transition;
- pending не способен навсегда заблокировать игрока;
- мир, созданный worldgen, реально участвует в ведении игры;
- мастер помнит значимые собственные ответы;
- исходы меняют нужные агрегаты, а не только список строковых фактов;
- multiplayer использует имена персонажей без Discord notification spam;
- все проверки из раздела 8 зелёные;
- повторный анализ не находит критических разрывов в целевом игровом цикле.
