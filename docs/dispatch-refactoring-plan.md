> Статус: маршрутизация полностью переведена на сценарную архитектуру 2026-07-14.

> Механический распил обработчиков из шага 4 также завершён: `MessageApplication`

> Ветка `develop-v2`.
> Основано на ревизии `src/masterclaw/app/message_handler.py` (2142 строки, из них ~1581
> незакоммиченных на момент анализа).

## 1. Цель

Пайплайн должен по **текущему стейту и вводу** принимать одно явное решение:

1. ответить детерминированно из стейта (статусы, каталоги, справка, отказ по режиму), или
2. запустить конкретный LLM-пайплайн с конкретным манифестом контекста, или
3. отказать / переспросить.

Сегодня это решение размазано по ~220 строкам `MessageApplication._dispatch` с
недокументированным порядком проверок и side-эффектами внутри принятия решения.
Каждый баг из плейтеста чинится добавлением ещё одного `if` в произвольное место цепочки,
что и порождает регрессии.

## 2. Диагноз: что именно сломано

### 2.1. `_dispatch` — стек заплаток, а не роутер

Перед LLM-классификатором стоит цепочка из восьми ad-hoc проверок (в порядке исполнения):

1. `_is_explicit_rules_question` — срабатывает раньше всего, **до** проверки режима,
   воркспейса и команд;
2. `match_information_intent` — с ручными (неполными) проверками режима;
3. воркспейс-FSM мира (`_world_workspace_action`);
4. команды (`_handle_command`, только при `workspace is None`);
5. возобновлённый бросок (`roll_for_confirmation_event`);
6. выбор мира из каталога (`_match_world_selection`);
7. «длинный фритекст = создание мира» (`_is_long_freeform`: ≥180 символов или ≥28 слов);
8. выбор преген-персонажа (`_match_pregenerated_character`).

Порядок несёт смысловую нагрузку, нигде не зафиксирован и не покрыт табличными тестами.
Вставка новой проверки в любое место меняет семантику всего, что ниже.

### 2.2. Четыре конкурирующих механизма определения интента

| Механизм | Тип | Где применяется | Проблема |
|---|---|---|---|
| `_is_explicit_rules_question` | префиксы + ключевые слова | до всего | обходит режим и воркспейс |
| `match_information_intent` (`deterministic_intents.py`) | списки фраз + Левенштейн (порог 15% длины) | дважды: строки ~187 и ~279, с разной защитой | двойной вызов с разным гейтингом; нечёткий матчинг по коротким фразам; захардкоженные фразы вроде «что ты умеешь» → `WORLD_LIST_REQUEST` |
| `_deterministic_world_intent`, `_deterministic_intent`, `_world_workspace_action` | regex `fullmatch` по дословным фразам | точечно | фразы дословно скопированы из транскриптов плейтестов; любая вариация формулировки тихо падает в default |
| LLM-классификатор (`pipelines/intent.py`) | typed pipeline | fallback | единственная ветка, проходящая через mode-gate |

### 2.3. Mode-gate применяется только к LLM-ветке

`_intent_allowed_in_mode` фильтрует результат классификатора, но все эвристики выше
обходят его. Инвариант «стейт решает, что доступно» соблюдается только для одной из
двух дисциплин.

Наблюдаемый баг-пример: игрок в режиме PLAY пишет «что ты умеешь» →
`match_information_intent` (второй вызов, строка ~279) возвращает `WORLD_LIST_REQUEST`
(фраза захардкожена в списке миров) → mode-gate отклоняет → игрок получает
«недоступно в режиме игры» вместо `HELP_REQUEST`.

### 2.4. Классификатор построен, потом отключён

В `MessageIntent` есть значения `WORLD_GENERATION_REQUEST`, `WORLD_CONFIRMATION_REQUEST`,
`WORLD_REVISION_REQUEST` — воркспейс мира проектировался под LLM-классификацию. Позже в
system-prompt классификатора дописано «Active world workspaces are handled by a state
machine before this classifier and will never be supplied here», а вместо него поставлен
`_world_workspace_action` на regex-`fullmatch` (например,
`r"сгенерируй мир и покажи(?: что получится| результат)?"`). Default при нераспознанной
фразе — `REVISE`: запрос «давай генерировать» молча уходит в LLM-пайплайн **ревизии**.
Это worst-case отказ: не ошибка, а неверное действие без сигнала.

### 2.5. Бог-объект `MessageApplication`

- Конструктор принимает **16 опциональных пайплайнов** (`... | None = None`), каждый
  с собственным fallback «unavailable» внутри обработчика.
- 2142 строки смешивают: маршрутизацию, воркспейс-FSM, матчинг каталога миров, матчинг
  преген-персонажей, разбор команд, все обработчики, рендер бросков, оркестрацию
  последствий и сборку контекста.
- Побочные эффекты происходят **во время** принятия решения: `record_activity`,
  переходы воркспейса, `claim` pending-взаимодействий.

### 2.6. Мелкий мусор (следы того же процесса)

- `ModeRouter.route(command=...)` — параметр мёртв (`del command` внутри); вызов
  передаёт `command=None` при уже вычисленном `command`.
- Дублирующийся возврат `conversation_clarification` в конце `_dispatch`
  (ветка `AMBIGUOUS` и default возвращают одно и то же).
- `_command_allowed_in_mode` пропускает произвольный сабкоманд через трюк
  `("/advance", subcommand)` — allowlist, который не является allowlist'ом.

### 2.7. Что здоровое и что НЕ трогаем

- `domain/routing.py` (`ModeRouter`) — чистый детерминированный роутер режимов.
- `context/manifests.py` + `context/assembler.py` — декларативные манифесты
  (пайплайн → роль модели → фрагменты правил → проекции стейта → бюджеты токенов).
- `pipelines/base.py` (`BoundedJsonPipeline`) — типизированные LLM-вызовы с валидацией.
- `app/orchestrator.py` — durable inbox/outbox, идемпотентность, батчинг.
- Телеметрия `intent_decision ... source=deterministic|llm` — сохранить и расширить.

## 3. Целевая архитектура

### 3.1. Контракт решения

Новый модуль `src/masterclaw/app/dispatch.py` (домен не трогаем — решение зависит от
интентов и манифестов, это app-слой):

```python
@dataclass(frozen=True, slots=True)
class DispatchSnapshot:
    """Всё, что нужно для решения. Собирается ДО решения, read-only."""
    mode: OperatingMode
    mode_reason: str
    game_id: str | None
    workspace_stage: WorldWorkspaceStage | None
    pending: PendingView | None          # id, kind, scene_id — без payload
    resumed_roll_id: str | None
    locale: str
    content: str
    author_id: str

@dataclass(frozen=True, slots=True)
class RespondFromState:
    """Детерминированный ответ: рендер из стейта, без LLM."""
    kind: StateResponseKind              # enum: WORLD_CATALOG, GAME_STATUS, CHARACTER_STATUS, ...

@dataclass(frozen=True, slots=True)
class RunPipeline:
    """Запуск LLM-пайплайна с конкретным манифестом."""
    pipeline: PipelineName
    handler: HandlerKind                 # enum: какой обработчик интерпретирует результат

@dataclass(frozen=True, slots=True)
class Reject:
    reason: str                          # ключ локали: unavailable_play, conversation_clarification, ...

@dataclass(frozen=True, slots=True)
class ClassifyWithLlm:
    """Детерминированных оснований нет — отдать LLM-классификатору."""

Decision = RespondFromState | RunPipeline | Reject | ClassifyWithLlm

def decide(snapshot: DispatchSnapshot) -> Decision: ...
```

Требования к `decide`:

- **чистая функция** — никаких обращений к store, никаких side-эффектов;
- один документированный список приоритетов внутри (см. 3.2);
- mode-gate применяется **внутри** `decide` ко всем веткам, включая эвристические;
- результат LLM-классификации прогоняется через тот же `decide`-совместимый гейт
  (`gate_llm_intent(snapshot, intent) -> Decision`), чтобы обе дисциплины проходили
  одну проверку.

### 3.2. Единый порядок приоритетов (фиксируется в docstring и тестах)

1. **Команды** (`/...`) — всегда распознаются первыми; допустимость по режиму — внутри гейта.
2. **Возобновление незавершённых взаимодействий** — подтверждение броска, pending-ответ
   (короткие «да/нет/число» и `player_narration`).
3. **Воркспейс мира** (если открыт) — FSM, но с изменённым default (см. 3.4).
4. **Детерминированные информационные интенты** — единый матчер, mode-aware с самого
   начала: `match_information_intent(content, mode)`. Фразы, валидные в нескольких
   режимах («что ты умеешь»), маппятся на разные интенты в зависимости от режима
   (`WORLD_LIST_REQUEST` в world_management, `HELP_REQUEST` в play).
5. **Детерминированные структурные триггеры** — выбор мира из каталога, выбор
   преген-персонажа, «длинный фритекст → создание мира» (только в world_management).
6. **`ClassifyWithLlm`** — всё остальное.

### 3.3. Один детерминированный классификатор вместо четырёх

Слить `_is_explicit_rules_question`, `match_information_intent`,
`_deterministic_world_intent`, `_deterministic_intent` в один модуль
`app/deterministic_intents.py` с единым входом:

```python
def match_deterministic(content: str, *, mode: OperatingMode,
                        workspace_stage: WorldWorkspaceStage | None,
                        pending_kind: str | None) -> MessageIntent | None
```

Правила:

- режим и стадия — **входы**, а не пост-фильтр;
- фразовые списки хранятся как данные (таблица «фраза → (режим, интент)»),
  каждый новый плейтест-кейс — строка таблицы + табличный тест, а не новый `if`;
- Левенштейн оставить только для точных коротких фраз-статусов; порог зафиксировать
  тестами на коллизии между списками (попарная проверка, что ни одна фраза одного
  интента не матчится на другой в пределах порога);
- при неоднозначном совпадении (две фразы разных интентов в пределах порога) —
  возвращать `None` (уйдёт в LLM), а не first-match по порядку итерации dict.

### 3.4. Воркспейс мира: вернуть классификатор или честный FSM

Вариант A (предпочтительный): подавать сообщения воркспейса в LLM-классификатор —
enum-значения `WORLD_GENERATION_REQUEST` / `WORLD_CONFIRMATION_REQUEST` /
`WORLD_REVISION_REQUEST` уже существуют; убрать из system-prompt оговорку про state
machine; regex-списки оставить как быстрый путь для точных совпадений.

Вариант B (если бюджет вызовов критичен): оставить FSM, но сменить default:
нераспознанная фраза в стадии REVIEW → **переспросить** («уточните: ревизия,
генерация или подтверждение?»), а не молча трактовать как ревизию. Действия
GENERATE/CONFIRM/EXIT — только по явному распознанному триггеру.

В обоих вариантах: логировать `workspace_action ... source=regex|llm|default`.

### 3.5. Распил `MessageApplication`

```
app/
  message_handler.py      → тонкий фасад: snapshot → decide → dispatch-таблица (< 200 строк)
  dispatch.py             → DispatchSnapshot, Decision, decide()      (чистая логика)
  deterministic_intents.py→ единый детерминированный классификатор    (чистая логика)
  handlers/
    world_management.py   → воркспейс-FSM, каталог, создание мира     (worldgen, world_intake)
    preparation.py        → персонажи, конфигурация, старт игры       (character, configuration)
    play.py               → действия, броски, нарратив, последствия   (action, narrative, consequence, ...)
    information.py        → статус-рендеры без LLM (character/game/xp/scene status, каталог, help)
```

- Каждая группа обработчиков получает в конструктор **только свои** пайплайны —
  исчезает конструктор на 16 опциональных аргументов.
- Побочные эффекты (`record_activity`, переходы воркспейса, `resolve_pending`) —
  только внутри обработчиков, после принятия решения.
- `HandlerResponse` / рендер панели статуса — без изменений.

## 4. Пошаговый план правок

Каждый шаг — отдельный коммит, зелёные тесты после каждого. Существующие тесты
(`test_message_handler.py`, `test_routing.py`, `test_play_flow.py`,
`test_preparation_commands.py` и пр.) — регрессионная сетка; их поведение меняется
только там, где текущее поведение признано багом (шаг 6, отдельно).

### Шаг 0 — зафиксировать текущее поведение (страховка)

- Написать характеризационные тесты на текущий порядок `_dispatch`: таблица
  «(режим, воркспейс, pending, текст) → какой обработчик вызван». Использовать
  фейковые пайплайны, ассертить по вызовам.
- Особо зафиксировать известные баги как `xfail` с комментарием
  (пример: «что ты умеешь» в PLAY → сейчас `unavailable_play`, ожидаем `HELP_REQUEST`).

### Шаг 1 — извлечь `DispatchSnapshot` и `decide()` без изменения поведения

- Создать `app/dispatch.py`; перенести логику ветвления из `_dispatch` в чистую
  `decide()`, сохранив текущий (кривой) порядок 1:1.
- `_dispatch` становится: собрать snapshot → `decide()` → таблица
  `Decision → обработчик`.
- Характеризационные тесты шага 0 проходят без правок.

### Шаг 2 — унифицировать детерминированный классификатор

- Слить четыре механизма в `match_deterministic(...)` (см. 3.3), фразы — в таблицу данных.
- Убрать двойной вызов `match_information_intent`.
- Добавить тест попарных коллизий Левенштейна между фразовыми списками.

### Шаг 3 — единый mode-gate

- Перенести `_intent_allowed_in_mode` внутрь `decide()` / `gate_llm_intent()`;
  применять ко всем веткам, включая эвристические short-circuit'ы.
- `_command_allowed_in_mode`: убрать трюк `("/advance", subcommand)`, задать явный
  allowlist сабкоманд.

### Шаг 4 — распил обработчиков по режимам

- Вынести обработчики в `app/handlers/{world_management,preparation,play,information}.py`.
- Конструкторы групп принимают только свои пайплайны; `MessageApplication` собирает
  группы (композиция в `cli.py` / фабрике меняется соответственно).
- Механический перенос, поведение не меняется.

### Шаг 5 — воркспейс мира

- Реализовать вариант A или B из 3.4 (решение принять до начала шага; по умолчанию — A).
- Убрать из system-prompt классификатора оговорку про state machine (при варианте A).

### Шаг 6 — исправить зафиксированные баги (снять `xfail`)

- «что ты умеешь» в PLAY → `HELP_REQUEST`.
- Нераспознанная фраза в воркспейсе → уточнение, а не молчаливая ревизия.
- `_is_explicit_rules_question` — подчинить общему порядку приоритетов
  (правила отвечаем в любом режиме, но **после** команд/pending/воркспейса).
- Мелочи из 2.6: мёртвый параметр `command` у `ModeRouter.route`, дублирующийся
  `conversation_clarification`.

### Шаг 7 — телеметрия и документация

- Расширить лог `intent_decision`: `source=command|pending|workspace|phrase|structural|llm`,
  плюс `gate=allowed|rejected`.
- Обновить `docs/v2-implementation-status.md` и `docs/architecture.md` (раздел о
  диспетчеризации), сослаться на этот документ.
- Прогнать полный чек-лист: `ruff check`, `ruff format --check`, `pytest --cov`,
  `masterclaw doctor`; затем плейтест на cheap-tier модели (grok-4.1-fast) — она
  быстрее всего вскрывает дыры в маршрутизации.

## 5. Критерии готовности

1. `decide()` — чистая функция; покрыта табличными тестами
   «(режим, воркспейс, pending, текст) → Decision» (≥ 1 тест на каждую строку таблицы
   приоритетов и каждый известный плейтест-кейс).
2. В `_dispatch`-фасаде нет ни одного текстового матчинга — весь он в
   `deterministic_intents.py`.
3. Mode-gate невозможно обойти: любой ответ игроку проходит через единый гейт
   (проверяется тестом: интент, запрещённый в режиме, отклоняется независимо от
   источника — фраза или LLM).
4. Ни один конструктор не принимает больше 6 пайплайнов.
5. Нераспознанный ввод никогда не приводит к молчаливому действию — только к
   уточняющему вопросу или LLM-классификации.

## 6. Правило для будущих фиксов (анти-дрейф)

Любой баг маршрутизации из плейтеста чинится **только** одним из способов:

1. строка в таблице фраз `deterministic_intents.py` + табличный тест;
2. правка промпта LLM-классификатора + тест на `gate_llm_intent`;
3. явное изменение таблицы приоритетов в `decide()` + обновление этого документа.

Добавление `if` в `message_handler.py` или новый матчер-хелпер — запрещено; такие
патчи отклонять на ревью.
